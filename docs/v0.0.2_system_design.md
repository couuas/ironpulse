# IronPulse v0.0.2 - 软件架构与同步设计说明书 (SDD)

## 1. 架构概览

v0.0.2 版本将单体纯本地架构升级为 **分布式双轨架构 (Local-First + Sync)**。
整个系统分为两个独立可运行但又紧密协作的部分：
1. **Frontend PWA (基于 Vite + React + Dexie)**：负责所有的 UI 渲染、本地存储与核心计算。依然保持 100% 的本地可用性。
2. **Self-Hosted API Server (基于 Node.js + SQLite)**：负责多设备间的数据中转、身份鉴权与备份，本身不承担任何业务逻辑计算。

## 2. 数据库设计 (Database Schema)

### 2.1 前端 Dexie 本地库变更 (Version 3 迁移)
为实现增量同步，我们需要在所有核心数据表（`exercises`, `routines`, `workouts`, `workoutSets`, `bodyMeasurements`, `personalRecords`）中注入同步元数据：
- `syncStatus` (枚举)：
  - `0` / `synced`: 已与服务器完全同步。
  - `1` / `pending_create`: 本地新建，待推送到云端。
  - `2` / `pending_update`: 本地修改，待推送到云端。
  - `3` / `pending_delete`: 本地执行了软删除，待告知云端。
- `updatedAt` (时间戳记)：用于冲突解决。
- `isDeleted` (布尔值)：实现软删除 (Soft Delete) 以确保删除动作能被追踪和同步。

### 2.2 后端 SQLite 表结构
后端采用极简的关系型模型，所有数据通过 RESTful API 进行批量存取。核心建表原则：
- 所有实体表必须包含 `user_id`，以实现多租户隔离。
- 主键 `id` 由前端生成（UUID / NanoID），后端仅作存储，不使用自增 ID，避免分布式环境主键冲突。
- 所有表均包含 `updated_at`、`created_at` 以及 `is_deleted`。

## 3. 同步机制设计 (Sync Protocol)

同步过程分为 **Pull (拉取)** 与 **Push (推送)** 两个独立阶段。采用基于时间戳的增量同步策略。前端全局维护一个 `last_sync_timestamp`。

### 3.1 Pull 机制 (Server -> Client)
1. 前端向后端发起 `GET /api/sync/pull?lastSync={timestamp}` 请求。
2. 后端查询所有 `updated_at > lastSync` 的记录（包含已软删除的记录），并按实体类型分组返回。
3. 前端接收到数据后，基于 **Last-Write-Wins (LWW, 最后写入者胜)** 策略与本地数据进行合并：
   - 如果云端记录的 `updatedAt` > 本地记录的 `updatedAt`，则覆盖本地数据，并将本地 `syncStatus` 标记为 `synced`。
   - 如果本地记录的 `updatedAt` 较新且状态为 `pending_*`，则保留本地修改（将在稍后的 Push 阶段覆盖云端）。
4. 冲突解决后，更新本地的 `last_sync_timestamp`。

### 3.2 Push 机制 (Client -> Server)
1. 前端扫描所有表，提取出 `syncStatus` 为 `pending_create`, `pending_update`, `pending_delete` 的记录。
2. 将这些批量变更打包，向后端发起 `POST /api/sync/push` 请求。
3. 后端接收数据，同样采用 LWW 策略（对比数据库内的 `updated_at`），将其 upsert 写入 SQLite。
4. 后端响应成功后，前端将刚才推送的记录在 Dexie 中的 `syncStatus` 修改为 `synced`，如果是 `pending_delete` 则执行物理删除。

### 3.3 触发时机
- **自动触发**：
  - 应用启动 (App Launch) 时静默触发一次 Pull -> Push。
  - 每次完成一次训练结算 (Workout Complete) 时静默触发 Push。
  - 触发网络恢复 (online 事件) 时触发同步。
- **手动触发**：用户在 Settings 面板中点击“立即同步”。

## 4. 接口协议与鉴权设计

### 4.1 接口列表
- `POST /api/auth/register`: 注册（对于自建服可配置是否开放注册）
- `POST /api/auth/login`: 登录，签发 JWT
- `GET /api/sync/pull`: 拉取增量数据
- `POST /api/sync/push`: 上报增量数据

### 4.2 CORS 与 安全性
- 后端需严格配置 CORS，允许来自用户指定的前端域名（如 Vercel 生成的域名）或 `*` 的跨域请求。
- 所有 `* /api/sync/*` 路由强制校验 `Authorization: Bearer <Token>` 请求头，校验失败返回 401。
