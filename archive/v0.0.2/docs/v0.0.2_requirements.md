## 1. 产品演进背景与 v0.0.2 愿景

在 v0.0.1 版本中，IronPulse 完美确立了 **Local-First (本地优先)** 的核心基调，提供了地下室断网环境下的 0ms 响应打卡体验。然而，用户在面对设备更换、多设备（如 PC 端排课、手机端打卡）协同场景时，纯粹依赖 JSON 导入导出略显繁琐。

**v0.0.2 的核心愿景**是：在**绝对不牺牲 v0.0.1 离线体验**的前提下，引入基于 API 的增量数据同步机制。
我们不提供强制绑定的官方中心化云服务，而是支持：
1. **前端托管无缝化**：官方直接支持适配 Vercel、Cloudflare Pages 等现代 Serverless 平台的部署。
2. **后端自主可控 (Self-Hosted)**：提供一个极简的 Node.js + SQLite 后端开源方案，极客用户可通过 Docker 一键在自己的 VPS、树莓派或 NAS 上部署，并将前端连接至自己的私有服务器。

## 2. 核心功能需求 (Functional Requirements)

### 2.1 多模式无缝切换 (Hybrid Mode)
系统默认保持**纯离线模式**，数据仅存于 IndexedDB。
在设置页新增 **「数据与同步 (Data & Sync)」** 工作台：
- **API Endpoint 配置**：用户可手动输入自建的服务器地址（例如 `https://sync.my-ironpulse.com`）。
- **账号与鉴权**：支持在自建服务器上注册/登录账号，获取同步 Token。
- 模式切换是平滑的：即便配置了服务器且在弱网环境下，训练打卡的读写依然是 0ms 本地执行，同步行为将在后台静默（或手动）触发。

### 2.2 前端 CI/CD 与 SPA 路由支持
- 在应用根目录集成平台适配配置（如 `vercel.json` 或 `_routes.json`），确保用户在直接访问诸如 `/analytics`、`/settings` 等前端路由时，托管平台能正确回退到 `index.html` 而不是抛出 404 错误。
- 构建系统支持注入构建期的环境变量，便于一键打包携带默认 API 地址的静态资源。

### 2.3 自主部署后端服务 (Self-Hosted Backend)
- **极简依赖**：后端必须足够轻量，采用 Node.js (Express/Hono) + SQLite 的单体架构，无外部数据库（如 PostgreSQL/Redis）部署负担。
- **核心数据模型**：支持多租户（通过不同 Account 隔离），提供存储用户动作库、模板、历史记录、体态等实体的数据表。
- **容器化支持**：项目需提供 `Dockerfile` 与 `docker-compose.yml`，使得用户只需要运行一行 `docker compose up -d` 即可完成私有云搭建。

### 2.4 离线优先的增量同步引擎 (CRDT-lite Sync)
这是 v0.0.2 的技术难点与核心价值：
- **操作日志标记**：前端任何打卡、新建、删除操作，需在 IndexedDB 中打上对应的状态戳（`pending_create`, `pending_update`, `pending_delete`）。
- **Pull (拉取机制)**：获取服务器上自上次拉取时间戳之后的所有变更记录，并与本地数据合并。
- **Push (推送机制)**：将本地带有 `pending` 状态的数据批量推送到服务器，服务器确认持久化后，本地清除 `pending` 标记。
- **冲突处理 (Last-Write-Wins)**：以业务更新时间（`updatedAt`）为准，较新的操作覆盖较旧的操作。

## 3. 非功能性需求 (NFRs)

- **降级容灾**：当用户填写的自建服务器宕机、SSL 过期或网络中断时，应用不得阻断用户的正常训练打卡，必须给出优雅的“离线/同步失败”状态图标，并在网络恢复后自动恢复同步。
- **隐私与安全**：同步流量需支持 CORS 配置；用户鉴权应当采用主流且安全的 JWT 机制；数据库密码或 Token 需加密存储于本地。
- **后端资源消耗**：自建后端服务在空闲时的内存占用需控制在 100MB 以内，满足极客用户部署在 1核 512M 低配机器上的需求。
