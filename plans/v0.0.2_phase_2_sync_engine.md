## 一、 阶段研发目标

在 Phase 1 提供了底层 API 支撑后，本阶段将聚焦于**核心增量同步算法**的实现，并在前端打通从“输入配置”到“静默协同”的完整闭环。

## 二、 交付物与任务清单

### T2.1 后端同步网关 (Sync Gateway)
- [ ] 开发 `GET /api/sync/pull`：
  - 接收参数：`lastSync` (Unix 时间戳)。
  - 逻辑：从所有核心实体表中查询 `updated_at > lastSync` 且所属 `user_id` 等于当前请求者的全量记录。
  - 产出：以 JSON 格式结构化返回增量。
- [ ] 开发 `POST /api/sync/push`：
  - 接收参数：包含按实体分类的变更列表。
  - 逻辑：开启 SQLite 数据库事务，校验 `updated_at` 时间戳。若客户端数据较新，执行 `UPSERT` (Insert on conflict update) 并更新服务端时间戳；若包含软删除标记，则在云端执行对应软删除或物理删除。

### T2.2 前端 Dexie 本地存储升级 (Data Migration)
- [ ] 修改 `src/db/db.ts`，将数据库版本升至 Version 3。
- [ ] 为所有表新增三个核心字段：`syncStatus` (0-3), `updatedAt` (number), `isDeleted` (boolean)。
- [ ] 编写平滑升级脚本 (Upgrade Script)，将现有旧版本用户的数据字段初始化（如 `syncStatus: 1` 标记为未同步，准备首次 Push）。
- [ ] 拦截并重写底层的增删改查逻辑（例如统一封装 `saveExercise` 函数），自动维护 `syncStatus` 与 `updatedAt`，物理删除改为将 `isDeleted` 设为 `true`，`syncStatus` 设为 `pending_delete`。

### T2.3 前端 Sync 调度中心 (`SyncService`)
- [ ] 编写 `syncService.ts`。
- [ ] 实现 `performPull(apiUrl, token, lastSync)`，解析远端数据并执行本地 LWW 覆盖更新。
- [ ] 实现 `performPush(apiUrl, token)`，筛选本地所有非 `synced` 记录，发送至云端，并在收到成功确认后，重置本地标志位。
- [ ] 实现 `fullSync()`，编排 Pull 与 Push 流程，更新并本地持久化全局的 `lastSyncTimestamp`。

### T2.4 用户交互层 (Sync Dashboard UI)
- [ ] 在应用设置 (`Settings`) 模块中新增二级路由或面板：“云端同步 (Cloud Sync)”。
- [ ] 界面提供输入框：“API 接入点 (Server Endpoint)”；以及“登录 / 注册”表单。
- [ ] 在登录成功后，展现当前账户信息、上次同步成功时间。
- [ ] 提供明确的“🔄 立即同步 (Sync Now)”按钮，附带 Loading 动效与失败/成功的 Toast 提示。

### T2.5 静默同步钩子 (Hooks)
- [ ] 在全局 `App.tsx` 或底层 provider 中注入生命周期检测：网络恢复 (`window.addEventListener('online')`) 和应用被切换至前台时，判断距离上次同步时间若大于 5 分钟，则静默发起后台同步。
- [ ] 在核心操作（如完成打卡）后，延迟 3 秒静默排队 Push。

## 三、 验收标准与跨设备实测流

- **容错降级验证**：切断网络或将自建服 API 地址故意填错，应用能在界面抛出静默的错误徽章，但不应有任何阻断型弹窗影响本地训练打卡。
- **跨端协同实测 (Happy Path)**：
  1. 打开浏览器 A (设备1)，登录账号，记录一次卧推的新突破。
  2. 观察控制台网络请求，确认增量 Push 成功。
  3. 打开浏览器 B (设备2，同一账号)，点击立即同步。
  4. 查验设备 B 的历史图表，卧推新记录应无损出现，且 `updatedAt` 时间戳一致。
- **冲突覆盖实测**：在断网环境下，设备 A 与 B 对同一自定义动作名称进行修改。恢复网络后，根据时间戳校验，后保存的修改应当正确覆盖掉前者的修改，杜绝产生脏数据。
